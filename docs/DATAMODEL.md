# Data model

What the prototype knows, where each fact lives, and how the facts are joined.
The app reads static JSON under `data/`, fetched once at boot; `store.js` adds
indexes and derived figures on top and never writes anything back. Seven of
the files are generated by `tools/generate-portfolio.js`, five are written by
hand — see `tools/README.md` for the generator and `ARCHITECTURE.md › Data` for
the current fixture counts.

## Entities

```
roles.roles ───────1:n──▶ projects.assignees[].role · meta.organisations[].role
meta.organisations ──1:n──▶ people.organisation
people ────────────1:n──▶ projects.assignees[].person projects.leadId = holder of the carrying role — PPE or PM — in the current quarter (derived)
                                                      projects.organisation = people[leadId].organisation (derived)
meta.portfolios ───1:n──▶ projects.portfolio
phases.eppm ───────1:n──▶ projects.phase · projects.bars[].phase · milestones.items[].subPhase
milestones.catalog 1:n──▶ milestones.items.code
projects ──────────1:n──▶ milestones.items.projectId · changes.projectId
meta.quarters[i] ───────▶ index i of every per-quarter array: assignees[].demand, gross, absence, external
```

Five rules hold the model together:

- **A project carries rows of a role and a person.** Each row is a role, the
  person who holds it — or nobody, for an open role — and that person's
  pensum per quarter. A role that changes hands is two rows. The project's
  demand, its lead and every person's load are sums or readings of the rows,
  derived in `store.js` and never written as fields.
- **A role is a function of the house.** The four roles are the ones SAP ePPM
  keeps on a project and this office plans: PFM, OM, PPE and PM. A role is
  held by somebody of a unit that does that work — a unit names the role its
  people hold — so a person has the same role on every project they are on.
- **A person belongs to an organisation; a project does not.** The unit is a
  fact about the person. A project reaches its unit through whoever carries
  it — the holder of Projektentwicklung or Projektmanagement, whichever has
  the larger pensum on it in the current quarter — and the join is one getter
  in `store.js`, so a project nobody carries has no unit and a handover moves
  the project with the person.
- **Time is one window.** `meta.quarters` lists the forty quarters the
  prototype covers, and every per-quarter array is indexed by position in that
  list. Index 0 is the first quarter of the window, which is also the current
  one. A quarter is named by an id of the form `2026Q3`.
- **A pensum is a share of a full position.** Every load figure — a project's
  demand, a person's booked load, the office's capacity — is a percentage of
  one full-time position, so `100` is one FTE and the figures add up across
  people and projects. The unit switch in the app divides by 100 for display.

## Files

### `meta.json` — the frame

| Field | Meaning |
| --- | --- |
| `org` | `name`, `division`, `app`, `unit`: the letterhead — the header prints office, division and application on three lines |
| `user` | the signed-in person: `personId`, `name`, `initials`, `role`, `signedIn` |
| `today`, `todayLabel`, `todayQuarter` | the fixed «now» of the fixtures, ISO date, display date, quarter id |
| `asOf`, `lastVisit`, `version` | the data stamp in the footer, the last visit for the notification badge, the version line |
| `quarters[]` | the window: `{ id, label, short, year }`, e.g. `2026Q3`, `Q3/2026`, `Q3`, `2026` |
| `portfolios[]` | the Teilportfolios: `{ id, label }` |
| `organisations[]` | the eight units: `{ id, label, short, role, projectShare }` — `PPE I`, `PM Inland II` are the short forms the grid columns use; `role` is the id in `roles.roles` of the role the unit's people hold on a project; `projectShare` is the per cent of a contract the unit's people may spend on projects |
| `settings` | the office's rules that are not a unit's: `smallProjectMio`, the credit in Mio. CHF up to which a project counts as small |
| `footerLinks[]`, `prototypeNotice` | chrome |

`quarters` and `organisations` are written by the generator, from its
calendar and its `TEAMS` table; the rest is kept by hand and read back.

### `phases.json` — the ePPM chain (hand-written)

`eppm[]` is the ordered list of Teilphasen every project runs through:
`Vorstudien`, `22 Auswahlverfahren`, `31 Vorprojekt`, `32 Bauprojekt`,
`53 Inbetriebnahme`, `61 Betrieb`, as `{ id, label }`. The id is the SIA
number, or `Vorstudien` for the BBL-specific first step. The order in the file
is the order of the chain; `eppmRank()` in `store.js` sorts by it.

### `roles.json` — the role catalogue (hand-written)

`roles[]` is the ordered list of roles a project may carry, as
`{ id, label, short, note?, lead? }`:

| `id` | `short` | `label` | |
| --- | --- | --- | --- |
| `pfm` | PFM | Portfoliomanagement | |
| `om` | OM | Objektmanagement | `note`: «Planungsbegleitendes FM», what the role does on a project — shown in the hint of a row |
| `ppe` | PPE | Projektentwicklung | `lead` |
| `pm` | PM | Projektmanagement | `lead` |

They are four of the roles SAP ePPM keeps on a project, in ePPM's order;
IL-BO, LIG, RL and Bearbeitende/r are kept there too and are not planned
here. The order in the file is the order of the rows under a folded-open
project. Written out, a role is its name followed by its short form —
«Projektmanagement PM» (`roleName()` in `store.js`, and `labelName()` for
a label the data carries, such as a person's function or the field of a
change); where there is no room, the short form stands alone.

`lead` marks the roles that can carry a project. A project goes by one name
where there is room for one — its unit, the line «Projektmanagement: …» in a
dialog, the mark that nobody carries it — and that is the holder of
whichever `lead` role has the larger pensum on the project in the current
quarter, the later role where they are level (`leadLane()` in `store.js`).
The two overlap where Projektentwicklung hands a project to
Projektmanagement. A unit whose role is not a `lead` — Portfoliomanagement,
Objektmanagement — never has a project «in» it: the «Organisation» filter
offers it on Personen and not where projects are listed.

### `people.json` — the roster

| Field | Meaning |
| --- | --- |
| `id` | stable slug, the key `projects.assignees[].person` points at |
| `name`, `initials`, `shortName` | display forms, precomputed |
| `role` | the function the person works in: the label of the role their unit names, and so of the role they hold on their projects |
| `employment` | the contract, in % of a full position |
| `organisation` | id in `meta.organisations` |
| `projectShare` | optional: the person's own project share in %, where it differs from the unit's. No fixture carries one yet |

A person carries no booked load. `personLoad()` sums the demand of the rows
the person has in a quarter over every project, indexed once per change of
state, and `personUtilisation()` turns it into a share of the person's project
capacity. Somebody who holds no role has no load and no utilisation; the
Personen tab prints a dash for them.

Nobody has their whole contract free for projects. `projectShare(person)`
reads the person's own share or, failing that, the unit's, and
`projectCapacity(person)` is `employment × projectShare / 100` — an 80 %
contract in a unit that keeps 20 % back carries 64 pensum points of projects.
That is the ceiling a person's load is measured against.

### `capacity.json` — the office as a whole

`gross[]`, `absence[]` and `external[]` are per-quarter arrays in % of a full
position for the whole unit; `net = gross − absence` is computed. `labels`
names the rows of the totals block under the planning grid. Capacity is
modelled at the level of the office, not per person: a person's ceiling is
their project capacity (see `people.json`), and absences are not per person in
this prototype. `gross` is still the sum of the contracts, without the project
share taken off — an open question: the office's utilisation is measured
against whole contracts while a person's is measured against their project
capacity.
`quarters` in this file is a leftover of the earlier eight-quarter window and
is not read; the arrays are indexed by `meta.quarters`.

### `projects.json` — the portfolio

| Field | Meaning |
| --- | --- |
| `id`, `number` | `pr51` and the four-digit display number `0051` |
| `title`, `location`, `kind` | «Ort, Strasse, Massnahme» and its parts |
| `phase` | the current Teilphase, an id in `phases.eppm` |
| `portfolio` | id in `meta.portfolios` |
| `priority` | `hoch`, `mittel`, `tief` |
| `credit`, `creditLabel` | the credit in Mio. CHF, or `null` and «offen» before the Baukredit is released |
| `preCredit` | whether the project is still before the Baukredit release; its demand is reported separately in the totals |
| `target` | the Soll-Pensum in % |
| `assignees[]` | who carries the project, in catalogue order of the roles: `{ role, person, demand[] }` — see below |
| `bars[]` | the phases that touch the window: `{ phase, from, to, label }`, in quarter offsets from index 0; `from` is negative for a phase that began before the window, and `continues: true` marks the last bar of a chain that runs on behind it |

A row is `{ role, person, demand[] }`: the id in `roles.roles`, a `people.id`
or `null` for an open role, and the pensum per quarter in % of a full
position. A pair of role and person appears once per project; a role that
changes hands at a quarter boundary is two rows, the one with noughts from
that quarter on and the other with noughts before it. The generator draws a
role as a pensum and the runs of quarters a person holds it for, and writes
one row per person. The rows stand for master data from SAP ePPM: the app
reads which there are and whose, and writes one thing, a figure typed into a
cell, into `demand[]`. A row emptied to its last quarter is still a row.

Four facts the file used to carry are readings of the rows, defined on every
project at load time in `store.js`: `demand[]` is the sum over the rows, kept
as a plain array and recomputed after every edit; `leadId` is the holder of
the carrying role in the current quarter, or `null` (`leadOf()`, see
`roles.json`); `unassigned` is its absence; and `organisation` is that
person's unit. The column, the filter,
the dashboard cards and the export all read them and see the same answer.

### `milestones.json` — the gates

`catalog[]` names the six Hauptphasen as `{ code, name, short }` — `1
Strategische Planung` … `6 Bewirtschaftung`. In the interface they are the
milestones: each is the gate that closes a Teilphase.

`items[]` is one gate per project and Hauptphase:

| Field | Meaning |
| --- | --- |
| `id` | `ms-51-4`: the digits of the project's id and the gate code |
| `code` | the Hauptphase, a key in `catalog` |
| `projectId`, `subPhase` | the project, and the Teilphase this gate closes |
| `plan`, `planDate` | the planned quarter id and the planned date, shortly before the phase ends |
| `forecast`, `forecastDate` | the current forecast |
| `status`, `statusLabel` | `ok`, `late` or `pending`, and its German label |
| `impact` | one line on what a slip means |

The bar plan places a gate at `planDate`; the notifications list the late
ones; the dashboard counts the gates whose `plan` is the current quarter.

### `changes.json` — the history

A flat list, newest first: `{ id, date, dateLabel, actor, projectId,
projectLabel, field, change, value }`. `value` is the before-after text
(«30 % → 35 %»). The bell counts the entries on the reader's projects that are
newer than `meta.lastVisit`; `onLanding`, which some entries still carry, is
read by nothing. The app prepends to it in
memory for every edit made in the session — a pensum typed into a cell, a
person chosen for a role, a changed rule — under the role's label as `field`;
nothing is written back.

### `dashboard.json` — what is not derived

The card menu's labels and the one card whose figures are not computed from
the projects: `creditByYear`, credit by year of realisation, as
`{ label, value, valueLabel, note }` rows. Every other dashboard card is
derived from `projects.json` at render time and follows the filters; this one
does not.

### Hand-written files

- `i18n.json` — `languages` and `terms`: the German string is the key and the
  fallback, each entry carries `en`, `fr`, `it`.
- `print.json` — the letterhead, legend and notes of the printed report.
- `roles.json` — the role catalogue, see above.
- `openapi.json` — the API the prototype would talk to. Its schemas are the
  richer model the office will need — `Allocation` and `Target`, `Absence` per
  person, a `PersonCapacity`. It was written before a project carried roles
  and has not followed: its `Allocation.role` is a job title, not one of the
  four roles; its person is required, so an open role cannot be said; and
  `Project.lead` is a stored field where this model derives it. Read it as a
  sketch of the service, not as the schema of these files.

## Derived in the app

`store.js` builds these once at load and again on every edit; nothing here is
in a file.

| Derived | From |
| --- | --- |
| `peopleById`, `projectsById`, `rolesById`, `portfoliosById`, `organisationsById`, `quarterIndex` | the lists above |
| `project.demand[]`, `project.leadId`, `project.unassigned`, `project.organisation` | the rows: the sum, the holder of the carrying role now, its absence, that person's unit |
| `cellValue(p, q)`, `projectDemand(p)` | `demand[]`; an edit is written into the rows and the sum recomputed |
| `laneOf`, `peopleOn`, `holdersAt`, `unstaffedAt`, `assignedTo`, `assignmentsOf`, `activeSpan` | readings of the rows: who holds what when, per project or per person |
| `leadLane(p)`, `leadOf(p)`, `carriesProjects(unit)` | the row a project goes by and the person on it; whether a unit's role is one that carries projects |
| `projectShare(person)`, `projectCapacity(person)` | the person's share or the unit's; `employment × share / 100` |
| `personLoad(id, q)`, `personUtilisation(id, q)` | the sum of the rows the person has in the quarter, indexed per change of state; divided by `projectCapacity` |
| `totals(list)` | per quarter: `demand`, `preCredit`, `external`, `net`, `utilisation = demand / net`, `free = net − demand` |
| `filteredProjects()`, `groupProjects()` | the state's search and filters; the fixed grouping by project size |
| `periods()` | the visible columns: quarters, or years and months folded from them, at the current offset |
| `kpis()` | projects in scope, credit total, pensum total, gates this quarter |

## Conventions

- Ids are stable slugs (`sonja`, `pr51`, `ppe-1`, `verwaltung`), so a shared
  link survives a renaming.
- Dates are ISO `YYYY-MM-DD`; where a display form is needed the file carries
  it precomputed (`dateLabel`, `todayLabel`, `creditLabel`).
- Credits are in Mio. CHF as numbers, `null` where none is released.
- Labels are German in the files; the interface translates through `t()`.
- The generator is deterministic and rewrites all seven generated files in
  one run; the story projects in `tools/seed/` are overlaid on the generated
  portfolio by id.
